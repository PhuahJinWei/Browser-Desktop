# 13. OCR is a model, not a library, and the desktop finds the lines itself

Status: accepted (M4) · **retired** by [ADR 15](./0015-no-on-demand-models.md): reading text out of pictures is
removed with the rest of the on-demand models. Kept for the record — in particular the backend
finding, which is the reason `preferredBackend` still has a comment about dispatch cost.

## Context

A scanned page is the one document the desktop could not read. `indexDocument` had a branch for it
since M1 — "no extractable text", recorded as skipped — with a comment saying OCR would arrive in
M4. This is that.

## The choice: TrOCR, not tesseract.js

The plan named tesseract.js, and called it "pragmatic, deterministic", which it is. It is also a
whole OCR engine with its own page-layout analysis, and it would have cost this project three
things it has been careful about:

- **A dependency and a binary in the repository.** Tesseract needs its worker, its WASM core and a
  trained-data file for the language. Self-hosting them is possible and necessary — the alternative
  is a CDN, and this page contacts exactly two hosts — but it means megabytes of committed binary
  and a second sync script.
- **A second kind of "model".** The desktop already has a model manager: consent before download,
  a SHA-256 per file, cache-keyed so the library never fetches anything itself, visible in the Task
  Manager, unloadable under memory pressure. Tesseract's assets would have sat outside all of it.
- **A second answer to "where do the weights come from".** TrOCR comes from `huggingface.co`, which
  is already one of the two hosts, under the same consent dialog as every other model.

TrOCR is 66 MB quantised, MIT licensed, and is a model like the others. What it costs instead is
that it is a **line recogniser**: no layout model, no word boxes, no columns. Hand it a page and it
reads the first line and stops.

## The consequence: the layout is ours to work out

`segment.ts` is the price of that choice. It binarises the page with Otsu's method, counts ink per
row, and reads text lines off the resulting projection profile — the oldest technique in document
analysis, and the right one for the case being claimed: dark text on light ground, upright, one
column. Each band is trimmed horizontally to its own ink so a short line is not handed to the model
as a mostly-blank strip.

It deliberately does **not** deskew, dewarp or detect columns. A photograph of a shop front is
beyond it, and the UI says so rather than failing quietly. `looksLikeText` rejects pages that are
mostly ink or whose "lines" vary wildly in height, because a photograph run through a line finder
produces dozens of bands that are really texture, and each one would cost a model pass.

## The measurement that changed the design

The backend. TrOCR is a vision encoder followed by an autoregressive decoder emitting roughly a
dozen tokens per line, and the plan's rule of thumb — heavy models prefer the GPU — pointed at
WebGPU. Measured on the same ten-line page:

| Backend       | Time      | Character errors |
| ------------- | --------- | ---------------- |
| WebGPU        | 18.4 s    | 2 of 270         |
| Threaded WASM | **3.1 s** | **0 of 270**     |

Six times faster, and more accurate with it — the WebGPU run misread "consignment" every time and
the WASM run never did. The reason is the same one M0 found for small embeddings: a dozen tiny
sequential decoder steps are dominated by dispatch cost, not arithmetic. So `preferredBackend`
gained `text-recognition` alongside `text-embedding` on the WASM side, and the rule of thumb lost
another case.

## Consequences

- Recognised text goes into the **ordinary document index**, through a new `indexText` that shares
  everything after extraction with `indexDocument`. A scanned page then turns up in Search with a
  snippet, ranked beside notes and PDFs. It is not a separate list of "OCR results" that nobody
  would open.
- `trocr-small-printed` was trained on receipts and **emits upper case regardless of the page**.
  Measured character accuracy is 100% case-insensitively on the sample scan and meaningless
  case-sensitively. That is a property of the model, not a bug to fix, and search is
  case-insensitive anyway.
- Reading is explicit, never automatic. Three seconds a page is cheap enough to offer and far too
  expensive to spend on every picture someone imports.
- The sample set gained a scanned delivery note, rendered by the desktop like every other fixture:
  off-white ground, speckle, uneven exposure, and no rotation — because rotation is exactly what
  this cannot handle, and a fixture chosen to hide that would be measuring the wrong thing.
- A better line finder is the obvious next step, and a text-detection model (DBNet, CRAFT) is the
  obvious way to get one. That is a second download and a much larger claim, so it is not here.
